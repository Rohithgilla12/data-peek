## Design Context

### Users

Developers (backend engineers, full-stack devs, data-curious builders) who need to quickly peek at database contents, debug queries, and explore schemas. They're typically mid-task — checking a migration, verifying data, or writing a query — and want to get in, get answers, and get out. They value speed and keyboard efficiency over visual polish.

### Brand Personality

**Fast. Honest. Modern devtool.**

- **Fast**: Sub-2-second launch, instant query results, no loading spinners where avoidable. The UI should feel like it responds before you finish thinking.
- **Honest**: No bloat, no telemetry, no dark patterns. Honor system licensing. What you see is what you get.
- **Modern devtool**: Feels like it belongs alongside Linear, Raycast, and Warp — not alongside DBeaver or pgAdmin. Clean, opinionated, keyboard-first.

### Emotional Goals

- **Confidence**: Users should feel in control of their data at all times
- **Calm focus**: The interface recedes — data and queries are the protagonist
- **Speed**: Every interaction should feel instant and effortless

### Aesthetic Direction

**Visual tone**: Minimal, technical, monospace-native. The UI is a tool, not a destination. Dense where useful, spacious where it aids scanning.

**References**:

- **Linear** — Command palette, keyboard-first, clean dark mode, information density without clutter
- **Raycast** — Speed-first interaction model, minimal chrome, results-focused

**Anti-references**:

- **DBeaver / pgAdmin** — Cluttered toolbars, nested dialogs, enterprise-heavy chrome, overwhelming options
- Anything with wizard flows, tab explosions, or gratuitous icons

**Theme**: Dark and light mode, system-preference aware. Dark mode is the primary design target.

### Color System

**Canonical accent**: OKLCH blue (hue 250°). The desktop app is the source of truth — marketing site and docs should align to this.

- Light: `oklch(0.45 0.15 250)` — deep, confident blue
- Dark: `oklch(0.65 0.15 250)` — lighter blue for dark backgrounds
- Blue was chosen over cyan for its familiarity and readability across both themes

**Palette summary**:
| Role | Light | Dark |
|------|-------|------|
| Background | `oklch(0.985 0 0)` | `oklch(0.16 0.005 260)` |
| Foreground | `oklch(0.14 0 0)` | `oklch(0.92 0 0)` |
| Primary accent | OKLCH blue (hue 250°) | OKLCH blue (hue 250°) |
| Destructive | Red-orange | Red-orange |
| Muted | Subtle blue tint | Subtle blue tint |

### Status and Category Colours

Colour is a token, never a raw Tailwind palette class. Status tokens say how something is going; categorical tokens only tell _kinds_ apart (data types, object kinds, tab types, chart series) and are never used for status. Tokens live in `apps/desktop/src/renderer/src/assets/global.css` and are exposed as `text-success`, `bg-warning/10`, `text-cat-blue`, and so on.

**Status** (with the existing `--destructive`; info and neutral highlight use `--primary`):

| Token | Light | Dark |
|---|---|---|
| `--success` | `oklch(0.52 0.14 155)` | `oklch(0.72 0.15 155)` |
| `--success-foreground` | `oklch(0.98 0 0)` | `oklch(0.15 0 0)` |
| `--warning` | `oklch(0.56 0.13 70)` | `oklch(0.80 0.14 80)` |
| `--warning-foreground` | `oklch(0.15 0 0)` | `oklch(0.15 0 0)` |

**Categorical** (one tuned shade per hue per theme; `--chart-1` to `--chart-5` point at blue, cyan, green, yellow, orange):

| Token | Hue | Light | Dark | Used for |
|---|---|---|---|---|
| `--cat-blue` | 250 | `oklch(0.55 0.14 250)` | `oklch(0.72 0.13 250)` | numeric types, table-preview tabs |
| `--cat-cyan` | 210 | `oklch(0.53 0.11 210)` | `oklch(0.75 0.11 210)` | functions |
| `--cat-green` | 155 | `oklch(0.53 0.13 155)` | `oklch(0.74 0.13 155)` | text types |
| `--cat-yellow` | 95 | `oklch(0.54 0.12 95)` | `oklch(0.82 0.13 95)` | booleans |
| `--cat-orange` | 55 | `oklch(0.56 0.15 55)` | `oklch(0.75 0.14 55)` | dates and times, procedures |
| `--cat-purple` | 300 | `oklch(0.55 0.15 300)` | `oklch(0.72 0.14 300)` | uuid, views, ERD tabs |
| `--cat-pink` | 350 | `oklch(0.56 0.16 350)` | `oklch(0.74 0.14 350)` | json, sequences |
| `--cat-teal` | 180 | `oklch(0.53 0.10 180)` | `oklch(0.76 0.11 180)` | materialized views |

Rules:

- Migrate by meaning: errors become `destructive`, success and connected become `success`, warnings and dirty or pending become `warning`, info and emphasis become `primary`, kinds become the matching `cat-*`, neutrals become `muted-foreground`, `muted`, `border`, or `foreground`.
- Tinted status surface recipe: `bg-{token}/10 border-{token}/30 text-{token}`.
- Within one view, distinct kinds get distinct hues. Reusing a hue across unrelated views is fine.
- Every token used as text reaches 4.5:1 against `--background` and `--card` in its theme. If one fails, adjust lightness, never hue.
- No gradients or glows in app chrome: use flat token colours.
- Exempt, fixed by design: exported-image renderers (`query-editor/share-results-image.tsx`, `share-image-dialog.tsx`, `health-share-content.tsx`), Monaco themes in `sql-editor.tsx`, environment presets and user-chosen colours in `lib/environment.ts`, and `pokemon-buddy-store.ts`.

### Typography

- **Sans**: Geist Variable, for natural-language prose only
- **Mono**: Geist Mono Variable, the body font: queries, data, code, identifiers, labels, menus, buttons, and the marketing site (monospace-first identity)
- The desktop app uses mono as the base body font, reinforcing the technical identity

**Type scale** (overrides Tailwind in `@theme`; `text-xl` and above stay as Tailwind defines them):

| Class | Size / line height | Role |
|---|---|---|
| `text-2xs` | 11px / 16px | badges, counts, keyboard hints, inline metadata |
| `text-xs` | 12px / 16px | dense UI: tree rows, grid cells, menus, labels |
| `text-sm` | 13px / 20px | default control and body text, AI answer prose |
| `text-base` | 14px / 22px | dialog titles, section headings |
| `text-lg` | 16px / 24px | page-level headings (settings, empty states) |

11px is the minimum. No arbitrary sizes (`text-[10px]`); where an element no longer fits, fix its padding or height rather than shrinking the text.

**Font rule**: use `font-sans` for natural-language prose: AI answer text, dialog and alert-dialog descriptions, empty-state explanations, settings help text, and the Ask input placeholder. Identifiers, SQL, values, numbers, labels, menus, and buttons stay mono.

**Weights**: 400 by default, 500 for labels, active items, and emphasis, 600 for headings. No 700 or above in app chrome (exported-image renderers are exempt).

**Numbers**: use `tabular-nums` wherever numbers sit in a column or update live (row counts, durations, numeric grid cells, sidebar count pills).

### Icons

- **Library**: Phosphor (`@phosphor-icons/react`). `lucide-react` is not used in the desktop app or `packages/ui`.
- **Single entry points**: the desktop renderer imports icons only from `@/components/icons` (`apps/desktop/src/renderer/src/components/icons.ts`); `packages/ui` imports only from its own `src/icons.ts`. These modules re-export Phosphor components under names that describe _meaning_, not shape (`SuccessIcon`, `ErrorIcon`, `WarningIcon`, `SpinnerIcon`, `AiIcon`, `RefreshIcon`, ...). One meaning, one icon: add a new semantic name rather than importing a second glyph for the same idea.
- **Weight**: `regular` everywhere. `fill` only for a toggled-on state that has a `regular` off state (pinned, bookmarked, active sidebar section, starred).
- **Size**: pair the icon with the text beside it: `size-3` next to `text-2xs`, `size-3.5` (or `size-3` for inline metadata) next to `text-xs`, `size-4` next to `text-sm` and in toolbar buttons, `size-5` or larger for empty states.
- **No decoration**: no duotone, no colour fills on idle icons.

### Guardrails

`apps/desktop/src/renderer/src/__tests__/design-system-guard.test.ts` fails CI on: direct icon-library imports outside the two icon modules, raw palette classes (`text-red-500`, `bg-zinc-800`, ...), arbitrary font sizes (`text-[...]`), and weights above 600 (`font-bold`, `font-extrabold`, `font-black`). ESLint also bans `lucide-react` and direct Phosphor imports.

### Design Principles

1. **Data is the UI**: Query results, schemas, and data grids are the primary interface. Everything else (chrome, navigation, controls) should minimize its visual footprint.

2. **Speed over ceremony**: No confirmation dialogs where undo works. No wizard flows. Prefer inline editing, command palettes, and keyboard shortcuts over modal workflows.

3. **Dense but scannable**: Embrace information density (like a terminal), but use spacing, typography weight, and subtle color to create hierarchy. Never sacrifice scannability for compactness.

4. **Native, not web-feeling**: The app should feel like a native macOS/Windows/Linux tool — proper titlebar behavior, system font rendering, platform-appropriate shortcuts, no "website in a window" energy.

5. **Quiet confidence**: No flashy animations, no gradients in the app chrome, no decorative elements. Let the data speak. Use motion only for state transitions (expand/collapse, tab switching) and keep it under 200ms.
